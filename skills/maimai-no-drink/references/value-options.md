# 最低消费与加量备选

用户的目标餐品和份量是下限；默认先给精确份量最低实付，再给最多两个包含全部目标、无任何饮料的加量套餐或组合。用户明确只要指定份量时设置 exact_only=true，跳过加量搜索。加量推荐不授权下单或新增资源消耗。

## 搜索

读取全部菜单和套餐详情后，同时保留相关套餐合法配置中多出食物的候选。不能用“超过目标数量”剪枝删掉整个套餐；从包含目标的套餐加补齐单品、多个套餐组合构建备选，不为了凑金额添加不相关单品。两类候选共享每批100次核价/5分钟上限，并分别报告待核价范围，不声称穷尽。

默认“小额加价”展示阈值为精确需求最低整单实付 + 5元（extra_budget_fen=500），这是产品展示默认值，不是用户已同意多花钱，也不用于按未经核实的菜单价剪枝。用户明确上限时覆盖此值；budget_fen 是整单预算，精确方案超过预算要说明，所有加量备选不得超出。用户主动要求更多选择可扩展加价范围。

每个备选都要重新试算整单，包含配送、打包、券条件及其差异。排除必带饮料、缺目标食品、费用未知、过期、跨店和未授权积分/会员方案。不能把旧历史核价当成当前报价。

## 展示

- 按需买：实际餐品及份量、整单实付；仅相对同份量单点基准计算节省。
- 加量备选：实际餐品及份量、整单实付；相对上面的方案多付/少付多少，具体多出什么。额外主食也要明确，不能藏在“丰富套餐”里。
- 费用同价/更低但多带食物，也单列，让用户决定是否需要。
- 没有精确份量可购方案时：说明不存在已核价基准，列符合目标的加量备选实付；不编造“加几元”或“省几元”。
- 所有差价都是两笔整单实付之差。未知额外食品单价时不估值；汉堡、鸡块、薯条不能以件数简单相加排名。不称为“最值”，说明仅按加价从低到高列出备选。
- 没有已核实的小额加价方案时如实说明，不为了凑两档硬推高价套餐。

表达示例（仅模拟，不是门店报价）：按需买26元；多付3元共29元，多一份中薯，原本要的食物全部保留、没有饮料。是否需要中薯由你决定。
